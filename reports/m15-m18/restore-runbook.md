# M16 Bundle recovery drill

Run `pnpm run m16:restore:drill`. It creates disposable PGlite source/target databases and private upload directories under the OS temporary directory, uses an in-process offline model fixture, and removes the fixture afterward. Deployment environment variables, Provider configuration, keys and user databases are not used. Standard output is one machine-readable JSON report; an exception or a failed invariant returns exit 1. HTTP diagnostics go to standard error.

The drill creates two Workspaces with messages, attachments, immutable versions, Runs, Manifests, provenance, Journal history and a stopped collaboration. Each real Bundle is exported and validated through the production adapters. The first import stops after the durable `blobs-ready` checkpoint; the process-level store is closed, the original upload is removed, and a reopened store resumes from its retained encrypted recovery archive. Repeating activated import identities must not ingest again or invoke a model. The second Workspace imports independently.

The report compares full portable facts and graph objects/relations, verifies every restored ResourceVersion's bytes, checks the source is unchanged, rejects a malformed archive, and runs the existing read-only reconciliation. It also continues a restored conversation and repeats the same command identity; only one new offline model execution is allowed. Failure injection here is **between content publication and activation**, not an in-transaction crash; the existing transaction-fault suites cover SQL rollback.

This is evidence for Bundle → clean store and encrypted import-checkpoint recovery. It is **not** evidence that user-managed backup creation, location/status/reminders, or its Purge inventory is implemented. Those remain INH-131 and the other half of INH-284. The JSON keeps `managedBackup` and `externalAcceptance` as `pending` even when this drill passes.

## Constraint for managed backups

Reuse the existing encrypted archive adapter, content-lifecycle/Workspace/digest locks and checkpoint activation. Import checkpoints cannot represent a backup of a live Workspace: they deliberately reject an existing target. Managed backup metadata must therefore have its own durable lifecycle, and register the archive digest before retaining bytes so a failed SQL commit cannot leave an untracked readable copy. Publication must recheck the Workspace's Purge generation under the same lock; a snapshot taken before Purge cannot publish afterward. Ready backups must pin their ciphertext against archive GC, and every retained digest must enter the existing Purge key inventory. Recovery to a separate clean store must reseal resource bytes with that target's keys without sharing mutable content roots. A file copy or an untracked call to `retain()` is not a production backup implementation.
