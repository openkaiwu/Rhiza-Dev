# M16 managed backup and Bundle recovery

Run `pnpm run m16:restore:drill`. It creates disposable PGlite source/target databases and private upload directories under the OS temporary directory, uses an in-process offline model fixture, and removes the fixture afterward. Deployment environment variables, Provider configuration, keys and user databases are not used. Standard output is one machine-readable JSON report; an exception or a failed invariant returns exit 1. HTTP diagnostics go to standard error.

The drill creates two Workspaces with messages, attachments, immutable versions, Runs, Manifests, provenance, Journal history and a stopped collaboration. The first source is created through the managed-backup Application command, verifies repeated creation identity and a live archive pin beyond the import recovery window, then downloads authenticated ciphertext through the production backup lifecycle. The second source is an ordinary full Bundle export. The first import stops after the durable `blobs-ready` checkpoint; the process-level store is closed, the original upload is removed, and a reopened store resumes from its retained encrypted recovery archive. Repeating activated import identities must not ingest again or invoke a model. The second Workspace imports independently.

The report compares full portable facts and graph objects/relations, verifies every restored ResourceVersion's bytes, checks the source is unchanged, rejects a malformed archive, and runs the existing read-only reconciliation. It also continues a restored conversation and repeats the same command identity; only one new offline model execution is allowed. Failure injection here is **between content publication and activation**, not an in-transaction crash; the existing transaction-fault suites cover SQL rollback.

This provides locally verifiable managed Backup → clean store and Bundle → clean store evidence. The current JSON requires `managedBackup: passed`, one managed source, a successful permanent pin, zero semantic differences and a successful final reconciliation before `ok: true`. `externalAcceptance` remains `pending`. The older `restore-status.json` is retained as the previous Bundle-only observation; current backend status is in `managed-backup-status.json`. Production backup/restore UI, external disaster/retention observations and formal Gates remain open.

## Production endpoints and lifecycle

Use `POST /api/v1/workspaces/:workspaceId/backups` with an `Idempotency-Key` and `{}`. It returns the persisted operation with running/ready/failed/interrupted/purged status, logical `managed://` location and timestamps; HTTP 201 alone is not proof of ready. Repeating an identity returns its current status and never repeats archive creation. A manual retry uses a new key and `{ "retryOf": "previous-backup-id" }`, permitted only for failed/interrupted work. `GET` on the same collection returns the latest 50 owner-scoped operations and a seven-day reminder derived from the latest ready completion; it does not send notifications. `GET /api/v1/workspaces/:workspaceId/backups/:backupId/archive` streams a ready backup as a normal `.rhiza` Bundle. The existing `/bundle/preview` and `/bundle/import` on a separate clean store handle validation and checkpoint activation.

The server-managed location uses the existing encrypted import archive store and its key directory. Archive bytes and keys must both survive recovery; location text or an inventory row alone is insufficient. Restore reseals target ResourceVersion bytes into independent target content roots. Imported business facts do not copy the source's operational backup inventory or personal Graph views. No Provider credential is included.

Begin freezes facts and the Purge generation under the existing lock, reserves a sealed metadata receipt, and records running. The validated digest commits before retaining bytes. Publication rechecks generation and pending revocation under Workspace/digest locks. Ready backups are pinned beyond the import recovery window; failed/interrupted registered digests stay in Purge inventory even if final publication rolled back. Plaintext work files are cleaned before ready/failed. Cleanup failure leaves running; startup obtains runtime ownership, cleans abandoned directories, then marks operations interrupted without automatic work. Purge rejects running backup work and then revokes all affected retained archive keys through its existing checkpoint. An unrelated Workspace's independent archive survives. Authenticated downloads keep ownership through disposal, including disconnect handling.

`pnpm vitest run e2e/m16-managed-backups.e2e.test.ts --maxWorkers=1 --testTimeout=30000` covers lifecycle/restart, actual attachment/history restore, failed final SQL publication and explicit retry, ready GC pins, active-work protection, Purge revocation, Workspace isolation and inventory-preserving rollback. Use `pnpm run bundle:reclaim-imports` only under the existing maintenance ownership policy. New migrations 0039/0040 do not erase old tables or data; down migration refuses retained inventory/personal state. Deploy or roll back only to readers that recognize the current migration checksums.
