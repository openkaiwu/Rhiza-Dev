# Rhiza / 根系

> 让 AI 不只回答下一句话，也能理解你正在推进的整件事。

Rhiza 是一个以 Workspace 为边界、面向长期复杂协作的人与 AI 工作系统。它把容易失控的线性聊天，变成可以分支、组合、追溯和继续推进的工作网络；你可以看见模型读取了什么、决定哪些内容应该进入上下文，并在探索不断扩展时守住项目主线。

按照 **V4.2 设计与开发规划**，Rhiza 将依次建设两个核心产品：先是可长期日用的**可控上下文对话系统**，再是负责计划、调度、评估与迭代的**自动化工作流**。Rhiza 组织模型、Agent、工具与上下文，专业工作由合适的执行者完成。

Rhiza 目前处于 **Early Preview**。当前单机 Web 版本已可体验“多工作空间 + 分支对话 + 工作图谱 + 显式上下文 + 活动时间线”。多模型协作、完整回放与数据迁移体验、自动化工作流等仍是规划能力；设计版本 V4.2 不代表这些功能已经交付。

## 为什么需要 Rhiza

真实工作很少沿着一条聊天时间线前进。

你会从某句话展开追问，暂时验证一个假设，比较多个方案，引用旧讨论，推翻已经失效的结论，并在几天后重新回到主线。普通聊天会把这些过程全部堆在一起：历史越来越长，重要决定越来越难找，旧信息继续污染新回答，你也很难确认模型这一次究竟看到了什么。

Rhiza 希望改变的不是聊天窗口的外观，而是人与 AI 共同工作的基本单位：

```text
一条不断增长的聊天记录
            ↓
可分支的讨论 + 可组合的上下文 + 可追溯的工作状态
```

对话可以保留探索时的反复与分歧，真正有价值的事实、决定、约束和产物则逐步沉淀为长期资产。

## 你可以怎样使用 Rhiza

### 从局部问题开一条支线

遇到术语、反例或临时方案时，从相关消息或选中文字直接发起临时讨论。支线可以独立展开，也可以在形成结论后合并回主线，避免十轮局部追问淹没原来的目标。

### 把不同项目分开推进

为不同研究或项目创建独立 Workspace，在侧边栏切换、重命名、归档或恢复。各工作空间分别保存自己的讨论与上下文，活动时间线帮助你回看已记录的变更。这是本机单用户下的项目组织能力，尚不包含多人协作。

### 决定 AI 这一次应该看到什么

Rhiza 提供 Auto、Assisted 和 Strict 三种 Context 模式。你可以接受系统推荐，也可以固定、移除或明确排除某个节点、片段和文件。自动化负责减少操作，人保留最终控制权。

### 在图中理解一项长期工作

讨论节点、来源、引用、关联和合并关系会形成可导航的图。Chat 适合继续当前工作，Graph 适合回看全局、寻找分支并重新进入过去的讨论。

### 回答“这个结果是怎么来的”

每次正式模型调用都会冻结一份不可变的 Context Manifest，记录所用模型、输入来源、内容版本、选择理由、排除项和预算信息。历史回答不只留下文本，也留下当时的上下文证据。

### 按任务选择合适的模型

你可以接入多个 OpenAI-compatible 服务，发现和管理模型，并按当前任务切换供应商。Rhiza 的长期方向不是押注单一模型，而是让不同模型的使用过程可比较、可追溯，并始终服从同一份项目上下文。

## 适合谁

Rhiza 优先服务那些需要与 AI 长期共建复杂项目的人，例如：

- 研究人员：追踪假设、证据、反例与结论的演进；
- 产品经理与咨询顾问：维持问题边界，分离脑暴、决策和待验证事项；
- 软件工程师：把架构讨论、约束、排障支线和实现结果组织在同一工作空间；
- 分析师、律师与内容创作者：在大量来源和多轮推演中保持上下文可见、结论可追溯。

如果你的需求只是一次性问答，普通聊天通常已经足够。Rhiza 的价值会在讨论变长、分支增多、决定需要复用时逐渐显现。

## 当前可以体验

当前 Web Preview 已支持：

- 节点内多轮对话，以及停止、重试、重新生成、编辑重发和真实流式输出；
- 从消息或选中文字创建临时/正式支线，并选择性合并回主线；
- Conversation Graph 的创建、连接、搜索、缩放、平移、拖拽和持久化布局；
- Active / Recommended / Excluded Context 管理，以及 Auto / Assisted / Strict 三种控制模式；
- 面向每次模型调用的不可变 Context Manifest 和来源快照；
- 节点、对话片段和文件内容的本地 Context 推荐；
- 多供应商与模型管理、附件、Markdown、代码、公式、Mermaid、Reasoning、Tool Call 和 Token Usage 展示；
- 多 Workspace 创建、切换、重命名、归档与恢复，以及按工作空间隔离的内容访问；
- Workspace 活动时间线，查看已提交的业务变更；
- Chat 执行历史，查看每次模型调用的状态、冻结输入身份、错误、取消与重试谱系；
- 附件资源版本与内容完整性校验，以及默认的本机嵌入式数据库持久化；也可配置外部 PostgreSQL。

当前版本仍有明确边界：

- 这是单机、单用户的早期版本，尚无账号、团队协作或跨设备同步；
- 多 Workspace 已有基础管理入口；稳定 Project State、完整回放、导入导出和备份恢复仍待完善；
- 当前活动时间线记录业务变更；执行历史记录单次模型调用及其终态，但两者都不等于完整可回放工作流；
- 外部 Coding Agent 协作、任务编排、长期记忆和自适应模型路由仍属于后续路线；
- 多模型协作已正式纳入 M16，包括独立评审、互评、辩论与第二意见，当前尚未上线；
- 桌面客户端与跨平台 Host 强化安排在 M29；移动客户端尚未交付；
- Scope Cognition、自动记忆写入、Mind 等认知能力仍是研究假设，必须先通过基准与消融实验证明价值。

## 从现在走向远景

V4.2 明确采用 **Chat first, Workflow second**：先让 Chat / Graph / Context 达到可长期日用，再推进任务与自动化。下面是开发顺序，不是已发布功能清单。

| 阶段 | 用户将获得什么 | 交付边界 |
| --- | --- | --- |
| 1 · 对话基础收敛（M01–M11） | 数据隔离、资源完整性、变更记录、执行历史，以及后续的图谱投影、上下文与回放基础 | M01–M06 已有接受证据；M07 起仍在建设，整阶段尚未完成 |
| 2 · 日常 Chat 产品（M12–M17） | 完善 Chat / Workspace / Graph / Context 体验，加入多模型协作、导入导出与备份恢复 | M17 通过功能、恢复、性能和真实使用验收后，才进入后续主线 |
| 3 · 项目与执行能力（M18–M24） | 产物、知识、决策、任务、搜索与资源管理，更好的上下文推荐、执行观测、基础路由辅助及外部执行器接入 | 在 Chat 产品完成后，按真实依赖推进 |
| 4 · 自动化工作流（M25–M27） | 从目标到计划、执行、评估、修订与交付，再加入多 Agent 协作和用户授权后的 Full Auto | 依赖前序任务与执行能力；当前尚未实现 |
| 5 · 长期优化与平台（M28–M32） | 自适应路由、桌面与跨平台支持、记忆智能、插件生态和统一控制与观测 | 长期规划，随真实需求和验证结果推进 |

### 多模型协作：从不同判断中形成明确建议（M16 规划）

不同模型可能看到不同的证据、风险与解法。你将可以围绕同一份明确记录的上下文，让模型先独立回答，再按需交换意见、互评或辩论，最后形成综合建议。

第一轮独立输出默认互不可见；你决定参与模型、是否互看输出、最大轮数与 Token / 时间预算，并可随时停止。综合结果需要给出明确推荐、主要替代方案、关键分歧、适用条件和未解决风险，每个输出都应能追到模型与上下文来源。普通单模型聊天仍可独立使用，不会被强制升级为多模型调用。

### 自动化工作流：以质量达标作为交付条件（M25–M27 规划）

你给出目标、约束与预算，Rhiza 将协调外部模型、Agent、工具或人类完成工作，并检查结果；未达标时修订计划、补充上下文、咨询或重新分配执行者。**所有步骤执行完，不等于工作已完成**：只有满足验收和质量要求，才能交付。

Full Auto 需要用户授权。系统应主动处理可自行解决的执行问题；涉及目标变化、价值取舍、重大不可逆风险或无法消解的冲突时，再带着明确建议请用户决定。复杂工作应始终可理解、可纠正、可追溯，人保留最终控制权。

## 我们坚持什么

- **上下文应当可见**：你应该知道模型读取了什么、为什么读取，以及什么没有被读取。
- **建议先于自动修改**：系统可以观察和推荐，不应在没有授权时替你改变项目事实。
- **来源比摘要更重要**：摘要帮助理解，原始证据与 provenance 才负责追溯。
- **探索不等于正式决定**：AI 推荐、用户确认与项目当前有效状态必须保持区别。
- **人的控制权不可省略**：分支、合并、状态更新、模型路由和未来的任务委派都应可解释、可覆盖。
- **质量决定是否完成**：未来的自动化需要主动评估与迭代，以满足验收要求为目标，资源效率服务于结果质量。
- **复杂度需要被证明**：Prompt 能解决的问题不增加基础设施；简单状态能解决的问题不先建设庞大认知系统。

## 在本机体验

### 一键部署（推荐）

部署向导会检查并管理已有的 Rhiza 生产服务、验证 Node.js 与 pnpm、按需在项目内安装便携环境，并引导你选择默认或自定义端口、模型服务与数据库配置。

macOS / Linux：

```bash
./scripts/deploy.sh
```

Windows PowerShell：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/deploy.ps1
```

自动安装的运行时、PID 与日志保存在项目的 `.rhiza/` 目录中，不会修改系统级 Node.js。若检测到的服务不是由部署向导启动，向导会要求你回到原终端停止它，避免误杀其他进程。

### 手动启动

需要 Node.js 24 与 Corepack。克隆仓库后运行：

```bash
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env
pnpm run dev
```

打开 `http://127.0.0.1:4173`。默认配置使用 `var/rhiza.pglite` 中的嵌入式数据库，无需另行部署 PostgreSQL。如果选择外部 PostgreSQL，请在 `.env` 中配置可用的 `DATABASE_URL` 并先运行 `pnpm run db:migrate`。

如果 API 默认端口 8787 被本机占用或被系统保留，可在 `.env` 中设置其他端口，例如 `API_PORT=8790`；开发服务器的 `/api` 代理会自动使用同一端口。

首次进入后，在左上角“模型与 API 设置”中配置 OpenAI、OpenRouter、DeepSeek、SiliconFlow、Ollama 或其他 OpenAI-compatible 服务，并选择一个模型。也可以先在 `.env` 中提供默认服务：

```env
AI_BASE_URL=https://your-provider.example/v1
AI_API_KEY=your-secret-key
AI_MODEL=your-model-name
AI_PROVIDER_NAME=Your Provider
```

对于本机 Ollama 等可信的无鉴权服务，可将 `AI_ALLOW_NO_KEY` 设为 `true`。

从旧 JSON 存储版本升级时，请先备份原数据，再按[数据迁移指南](docs/runbooks/m05-domain-journal-migration.md)显式导入并核对结果；旧 JSON 文件不会自动成为当前数据库中的工作空间。

### 数据与隐私

Rhiza 默认把工作空间数据保存在本机。Provider API Key 使用本机生成的 AES-256-GCM 密钥加密后保存，不通过 API 回显，也不会提交到 Git。发送消息时，被选中的 Context 会交给你配置的模型服务处理，因此仍需遵守对应 Provider 的数据政策。

当前 Preview 尚未提供登录和多用户权限隔离，请勿把它作为开放公网的多人服务直接部署。
